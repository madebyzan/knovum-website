description: 从一个具体问题开始，完成收集、核查和交付，而不只是认识几个按钮。

## 开始前准备

安装并打开 Knovum，准备一篇短文章或 Markdown 文件，以及同一问题的另一份来源。导入、整理、关键词搜索和导出不需要服务商密钥。需要生成回答时，先配置 [AI 服务商](../../guides/providers/)或[桌面 Agent](../../guides/agents/)。

本例要回答：**为什么用户试用后不再继续？** 你可以替换成自己的问题。下面的名称和文字是练习材料，不是内置产品内容。

## 1. 建立有边界的工作区

从资料库创建 Space，命名为“试用研究”。添加笔记，写下问题，以及什么证据才足够支持结论。

可以从这段文字开始：

> 问题：为什么用户试用后不再继续？
> 需要：具体原因、每个原因的来源，以及目前仍不知道什么。
> 不要把一次访谈当成全部用户的代表。

**检查点：** Space 名称有意义，问题可见。先不用导入全部资料库，两份相关来源足以走通工作流。

## 2. 放入真正能读到的证据

使用“添加网站”保存文章地址，或用“导入文件”选择文档，再加入第二份来源。使用录音时，启动[转写](../../guides/transcription/)并等待完成。

分别打开资源，确认已经能读到正文或转写。保存了文件名不代表正文抽取完成。导入文件是托管副本，不是外部原件的同步链接。

**检查点：** 能读到计划使用的实际段落。只有标题时，先检查导入或抽取任务，不急着提问。

## 3. 明确哪些材料属于这个问题

将相关资料放入名为“证据”的区段，工作问题单独保留。需要整体移动多个对象时才使用分组；它和区段的用途不同。

在画布上找不到来源时，用大纲定位。定位会揭示所属分组或区段，不会新建一份副本。

**检查点：** 你清楚本次研究包含哪些材料，并能通过大纲返回来源。

## 4. 先自己找到一段原文

用问题或来源中的有辨识度关键词查找，打开结果，将匹配段落与原文比较。

语义搜索需要明确准备向量模型与索引。这次用关键词就够了，也能避免模型未准备干扰首次体验。

**检查点：** 至少一段相关原文已经亲自读过，不是只看生成摘要。

## 5. 提一个能审计的问题

选中相关来源，在提问或对话入口使用这一范围，选择可用执行目标。可以这样问：

> 这些资料提到了哪些放弃试用的原因？
> 每个原因都给出支持它的原文引用。
> 区分来源原话和你的解释。
> 来源冲突或信息不足时明确说明。

打开每条影响结论的引用：原文真的支持回答中的判断吗？它是当前引用，还是历史 detached 引用？回答流畅、链接看起来合理，都不构成核查完成。

**检查点：** 不依赖回答本身，你也能说明主要结论的依据。无法核查的判断应删除或标为未解决。

## 6. 保存结论，而不只保存一段回答

写一份笔记，分成“证据支持什么”“仍不确定什么”“下一步做什么”，保留相关链接或关系。需要正式产物时，从选中资料创建文档，再检查输入记录。

交付单份成果时导出文档。需要保留内容、资产和关系，或跨电脑迁移时，将整个 Space 导出为 `.knovumspace`。

**检查点：** 打开交付文件，或将包导入新 Space 检查内容。导出一篇文档不是备份整个工作区。

## 遇到问题先查哪里

| 现象               | 第一检查项                       |
| ------------------ | -------------------------------- |
| 导入文档只有标题   | 导入、正文抽取状态与受支持格式   |
| 录音查不到讲话内容 | 转写任务，不是服务商配置         |
| 语义搜索不可用     | 本地向量准备与当前索引           |
| 提问失败           | 选定执行器、凭据和操作支持       |
| 引用与原文不一致   | 来源修订及 detached/current 状态 |
| 没有可用导出项     | 资源准备状态和实际提供的格式     |

保留原件，不要通过删除数据库修复失败操作。接着阅读[结构化知识](../../guides/knowledge/)或[导出与迁移](../../guides/export/)。
